Чи може ШІ знаходити вразливості в коді краще за людину?

Студентська розвідка: порівнюємо ручний рев'ю коду та автоматизовану перевірку нейромережами.

25 жовтня 2026 · ~5 хв читання

Як виникла ця ідея

Коли я вперше сгодував ChatGPT шматок коду з курсової й він за секунду показав мені забудькувату помилку, у голові одразу виникло питання: "А навіщо тоді взагалі сидіти й годинами рев'ювити код вручну?". Здавалося, що професія рев'юера чи сек'юріті-аудитора тепер під загрозою. Але коли почав копати глибше під час підготовки цієї теми, виявилося, що все набагато цікавіше й не так однозначно.

Найбільше дивує інше: класичні загрози на кшталт SQL-ін’єкцій або XSS висять у топі OWASP Top 10 вже не один десяток років.[1] Про них знають усі, про них пишуть у кожному підручнику, але ми все одно продовжуємо допускати ці самі дитячі помилки у своїх проєктах.

Де людина все ще сильніша

Головна суперсила людини-аудитора — це розуміння бізнес-логіки. Нейромережа бачить тільки синтаксис, а людина розуміє, навіщо цей код написаний. Наприклад, якщо в умовному навчальному інтернет-магазині можна спокійно підмінити ціну товару через параметр у запиті й купити щось за нуль гривень — з точки зору коду все ідеально: змінні передаються, типи збігаються, помилок немає. Тільки людина зможе здогадатися, що тут є діра в логіці.

Але у людей є величезний мінус — ми банально втомлюємося. Коли сидиш над кодом уже третю годину поспіль (особливо десь о другій ночі перед дедлайном), очі замилюються, увага падає, і навіть очевидна склейка рядків у SQL-запиті починає здаватися нормальним рішенням. До того ж людський фактор робить перевірку суб'єктивною: один студент чи розробник помітить баг, а інший — пропустить.

У чому перевага штучного інтелекту

ШІ в цьому плані працює як робот-невтомник: йому байдуже, скільки зараз годин, він перевіряє тисячі рядків за лічені секунди й однаковий за точністю як на першому файлі, так і на сотому. Типові штамповані вразливості він клацає як горішки — відразу підкаже, де ми забули провалідувати вхідні дані або виставили критичні ключі прямо в код. І головне — він не просто каже "тут помилка", а й відразу пропонує готове виправлення.

Але сліпо довіряти йому точно не варто. Головні проблеми ШІ — це галюцинації та обмежене контекстне вікно. Модель може з максимально впевненим виглядом вигадати діру там, де її немає, або навпаки — прогледіти небезпеку, якщо вона розмазана по кількох різних файлах проєкту. Крім того, самі джерела показують: якщо розробник повністю покладається на ШІ-автодоповнення, свіжонаписаний код часто містить баги з безпеки.[5][6] Для таких випадків вже навіть створили окремий перелік ризиків.[2]

Мій висновок

Сформулювати чітке "ШІ повністю замінить людину" тут не виходить. Замість змагання краще працює зв'язка: ШІ виконує брудну та рутинну роботу, за секунди проганяючи базові перевірки, а людина включає мізки там, де потрібна логіка, розуміння архітектури та перевірка відповідей самого ШІ.

Зауваження: цей матеріал є оглядом існуючих джерел і статей, а не моїм власним повноцінним лабораторним дослідженням з точними вимірами у відсотках.

Приклади з практики

Ось два класичних приклади вразливостей, які найчастіше розбираються на заняттях з безпеки, та варіанти, як їх правильно закрити.

1. SQL-ін’єкція (Python, Flask + sqlite3)

Як робити НЕ треба
@app.route("/search")
def search():
    q = request.args.get("q", "")
    cur = db.cursor()
    # Конкатенація рядків — прямий шлях до проблеми
    cur.execute("SELECT id, title FROM books WHERE title LIKE '%" + q + "%'")
    return jsonify(cur.fetchall())

# Якщо ввести q = ' OR '1'='1  -> база віддасть усе підряд
Як зробити правильно
@app.route("/search")
def search():
    q = request.args.get("q", "")
    cur = db.cursor()
    # Параметризований запит: sqlite сам безпечно підставить значення
    cur.execute("SELECT id, title FROM books WHERE title LIKE ?",
                ("%" + q + "%",))
    return jsonify(cur.fetchall())

2. Міжсайтовий скриптинг / XSS (JavaScript)

Вразливий варіант
// Вивід коментаря на сторінку через innerHTML
function showComment(c) {
  const box = document.getElementById("comments");
  box.innerHTML += "<p><b>" + c.author + "</b>: " + c.text + "</p>";
}

// Якщо c.text = <img src=x onerror=alert(1)> -> скрипт виконається в браузері
Безпечний варіант
function showComment(c) {
  const box = document.getElementById("comments");
  const p = document.createElement("p");
  const name = document.createElement("b");
  name.textContent = c.author;       // Безобідний текст, без виконання HTML
  p.append(name, ": " + c.text);
  box.appendChild(p);
}

Документ виділяє головні загрози при роботі з LLM — від Prompt Injection до сліпої довіри до згенерованого коду. Головне правило: будь-який результат від ШІ потрібно сприймати критично й обов'язково перевіряти.

Американський стандарт рекомендує підходити до ризиків ШІ системно через 4 кроки: Govern, Map, Measure, Manage (Правила, Пошук ризиків, Оцінка та Керування).

У гайдах GitHub детально описано концепцію автоматичного сканування коду (Code Scanning), коли перевірка безпеки вбудовується прямо в процес розробки та CI/CD.
